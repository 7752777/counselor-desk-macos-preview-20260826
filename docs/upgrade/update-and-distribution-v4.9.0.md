# v4.9.0 更新与分发

## 更新清单

更新清单格式为 `cwb-update-manifest-1`，每个平台包至少包含：版本、平台、架构、HTTPS 地址、SHA-256、包签名、最低兼容版本、更新权益、强制更新标志和说明。清单本身由 Ed25519 签名，生产客户端必须配置公钥并拒绝无签名清单。

## Electron 流程

1. 启动后低频检查，用户手动点击可立即检查。
2. 下载到临时位置，校验清单签名、包哈希和 Electron 更新运行时的安装签名。
3. 安装前创建加密恢复点；SQLite、WAL、附件仓和工作区路径不变。
4. 用户确认后重启安装，不卸载旧版本。
5. 迁移或安装失败进入 `rollback-required`，保留旧版本和恢复入口。
6. 成功后展示版本、迁移结果和恢复点。

`desktop/update-runtime.cjs` 已提供可注入 `electron-updater` 的检查/下载/安装状态机。它先验签清单返回的原始 JSON，再规范化并选择当前平台包；下载完成后读取实际文件，复核 SHA-256，并在商业构建中要求平台签名校验器通过。`scripts/build-update-manifest.js` 生成未签名清单，`scripts/sign-update-manifest.js` 通过外部签名模块生成最终清单；`services/license-server` 可在验签后发布清单。当前仓库仍没有真实更新 CDN、平台签名证书或公证凭据，正式构建必须在 Windows/macOS 实机验证。

清单发布顺序固定为：构建平台包 → 计算 SHA-256 → 完成平台代码签名 → 生成包签名字段 → 生成清单 → 使用更新 KMS 签名 → 管理员发布 → 客户端验签和下载。清单签名密钥可以与许可证签名密钥分离，轮换时保留旧 `kid` 直到所有仍支持的客户端完成迁移。

发布工作流要求：Windows 设置 `WINDOWS_CSC_LINK`/`WINDOWS_CSC_KEY_PASSWORD`，macOS 设置 `MACOS_CSC_LINK`/`MACOS_CSC_KEY_PASSWORD`、`APPLE_ID`、`APPLE_APP_SPECIFIC_PASSWORD` 和 `APPLE_TEAM_ID`；商业构建还必须提供 `CWB_LICENSE_PUBLIC_KEYS_JSON`、`CWB_LICENSE_SERVICE_URL`、`CWB_UPDATE_FEED_URL` 和 `CWB_UPDATE_MANIFEST_URL`。任一凭据缺失即停止商业包构建；当前本地没有这些秘密，因此不能声称已完成平台签名或公证。

## 网页与离线包

网页端可以检查清单并刷新在线版本；单文件离线 HTML 不承诺后台自动更新，只提供版本检查和新文件下载提示。浏览器关闭后不能后台写文件，也不能替代 Electron 的无卸载安装流程。

## 分发层级

- GitHub 私有 Release：源码协作者和受控维护人员使用。
- 客户更新 CDN：只提供签名安装包和清单，不暴露源码和授权私钥。
- 授权服务：只提供许可证与设备接口，不保存学生业务数据。
- 备份存储：只接收用户选择的加密业务包，不接收许可证 token 或模型 Key。

只有完成产物签名、公证、清单发布、更新回滚和恢复演练后，才允许生成正式 `v4.9.0` Tag/Release。

## 2026-08-23 收口补充

候选代码现在把 `desktop/platform-signature.cjs` 接入 `desktop/update-runtime.cjs`：Windows 使用 Authenticode，macOS `.app` 使用 `codesign` + `spctl`，`.pkg` 使用 `pkgutil`，`.dmg` 使用 `spctl --type open`，`.zip` 解包后校验其中的 `.app`。平台命令通过参数数组执行，不把下载路径拼进 shell；签名器缺失、状态无效、发布者不匹配或平台未知时均拒绝安装。`tests/platform-signature.js` 只验证注入式分支，不冒充真实证书验收。

安装状态保存为用户数据目录下独立的 `vault/update-install-state.json`，只包含阶段、目标版本、恢复点元数据和错误码，不包含许可证 token、模型 Key 或学生业务内容。启动后如果版本没有达到目标版本，或新版本工作区健康检查失败，会调用恢复回调；当前目录先改名为 `failed-update-current-*` 保留，再切换经过校验的恢复点。回滚成功、回滚失败和失败原因都会写回状态文件；无法回滚时不会生成新密钥或删除失败副本。`tests/update-rollback.js` 覆盖安装器异常、旧版本重启和新版本成功恢复三条注入式路径。

本地代码已实现这些安全动作，但真实 Windows Authenticode、macOS Developer ID、公证、electron-updater 下载中断、安装器跨重启失败和恢复演练仍需在目标设备与生产 CDN 上取得证据。没有这些证据，`v4.9.0` 仍只能是商业候选。

## 2026-08-24 自动检查体验收口

Electron 商业构建在同时配置更新 feed 和签名清单地址后，会在启动约 30 秒执行一次自动检查，之后每 6 小时检查一次；应用退出时停止调度。调度器只负责触发检查，不负责静默下载或安装，避免用户正在录入数据时被重启打断。发现版本后，主进程通过 `cwb:update-state` 受限事件发送状态，界面显示“版本更新”入口和可操作的下载/安装按钮。

当前实现仍有三个必要前提：

- 许可证必须包含核心版本更新权益；没有授权或授权过期时不发送更新请求。
- 更新清单必须由外部签名服务生成，并包含当前平台包、SHA-256 和平台签名证据。
- 真实构建必须使用 Windows Authenticode 或 macOS Developer ID/公证；本地注入式测试只证明拒绝路径和状态机，不提供证书。

浏览器和单文件离线 HTML 不使用后台安装器。它们只能手动检查并重新下载新文件；用户数据需先导出/备份，再替换文件。更新服务上线前，默认开发构建不会自动访问空更新地址。

## 普通用户看到的更新流程

正式配置完成后，桌面端会在启动后约 30 秒自动检查一次，之后每 6 小时检查一次；检查只显示提示，不会在录入学生资料时突然下载或重启。用户也可以在“设置 → 版本更新”手动检查。

用户实际操作只有三步：

1. 点击“检查更新”，确认版本说明和所需更新权益。
2. 点击“下载更新”，等待清单签名、文件哈希和平台签名全部通过。
3. 点击“安装并重启”，应用会先创建恢复点，再完成无卸载升级。

升级成功后继续使用原工作区；SQLite、附件、局域网同步配置和学生数据目录不因安装包版本变化而迁移到安装目录。若安装、迁移或启动健康检查失败，系统保留旧版本、失败目录和恢复点，提供回滚/修复入口，不生成新密钥覆盖旧数据。

浏览器版和单文件离线包没有权限在浏览器关闭后自动替换自身。它们显示新版本提示，用户下载新的 HTML 后再打开；替换前应先在“备份与恢复”中生成备份。三端数据互通仍通过局域网主机或加密交换/备份流程完成，许可证状态不会随业务备份复制，换设备需要重新激活。

当前候选的更新体验已经有本地运行时、调度器、恢复和契约测试；要向客户开放真实更新，还必须补齐生产更新 CDN、签名清单、Windows/macOS 证书与公证，并完成至少一次跨重启实机回滚演练。
